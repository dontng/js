# 需求与已有决定

以下为项目技术需求的归纳，不存储个人背景或逐字聊天记录。确认的是需求和方向，不代表对应功能已完成。

## 需求

| 编号 | 用户需求 | 交付判断 |
|---|---|---|
| R01 | JS承接CAN/CAN FD到ROS2，并容纳未来仪器适配等探索 | 保留清晰主线，扩展按实际任务加入，不限制为关节模组单一产品 |
| R02 | 面向机器人软件测试与工具开发，积累可复用能力 | 以软件通信、自动化、工具维护和问题定位为能力目标 |
| R03 | 项目必须本人足够懂，不能AI一次写出大工程 | 每轮小功能；能解释运行、独立修改、验证结果及定位问题 |
| R04 | GitHub是开卷资料，上位机是长期答卷 | AI主动找可运行小示例与启发，不要求用户凭空想所有功能 |
| R05 | 收集需求、问题与阶段，让自己知道在做什么、问什么 | 本目录维护稳定问题编号、状态和证据 |
| R06 | 学习、资料、实验与工具分别管理 | 沿用现有目录，需求问题不淹没在普通笔记中 |
| R07 | 工作启发可转成自己的通用工具，公开内容有独立依据 | 尽量采用公开接口、独立实现、自造数据；不把内部原件改名后直接发布 |
| R08 | 每次提交详细说明并区分AI执行者 | 遵守现有提交规范，具体修改、原因、验证与真实署名齐全 |

## 已有方向

- 主语言暂定Python，具体设备SDK与现有上位机语言尚待确认。PySide6是当前界面候选，不是已经安装验证的决定。
- CAN学习以能独立接入、编程和排错为目标；后续进入ROS2，不能省略编码能力。
- 从GitHub选小效果，运行、理解、独立改动和排错后再并入JS；参考代码的来源与许可保留。
- 设备接入优先采用已验证的驱动环境；Linux/ROS2先评估Ubuntu 22.04＋Humble，实施前核实，macOS适配不作为当前阻塞。
- “脱敏”目前只有协作方向：提炼一般需求、使用公开依据及替代数据。此前复杂流程草稿未提交，不把它宣称为已经实现的功能或已批准的大型制度。

## 尚未作出的决定

第一套设备与SDK、正式GUI技术栈、第一款参考项目及具体功能组合均待确认。ROS2尚未安装；通用框架、仪器适配清单与开发进度不能提前写成事实。

学习验收四问：它怎样运行？改行为要改哪里？如何证明改对？出错先查什么？
