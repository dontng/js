# 问题驱动的自我迭代

JS的问题管理是一个持续循环：**提出问题 → 拆成可行动的小问题 → 查资料/给出解释 → 本人修改或实验 → 根据证据回看 → 解决、修正或重新打开 → 提出下一问**。
这里的“自我迭代”指学习者与项目依据结果持续调整，不是AI无人监督自动扩张需求。

## 每一轮怎样推进

1. **选问题**：从当前任务或收件箱选一项，写清为什么值得现在解决、依赖什么。
2. **判断是否需要拆分**：如果不能用一个小解释或实验推进，先拆到能动手；小问题不必强行拆。
3. **形成暂定回答**：从GitHub、官方资料、获准使用的参考说明或自己的分析获得候选解释，区分来源与推断。
4. **本人验证**：概念问题用自己的话解释、对照例子；代码问题本人改一处行为、运行验证并排查错误。按实际问题选择证据，不统一强加实机实验。
5. **回看结论**：哪些已确定，哪些仍不成立？已解决、待验证或暂缓分别记录。答案不成立时改正，旧判断只留必要轨迹。
6. **产生下一问**：记录发现的新问题、为什么出现、是否阻塞当前目标。候选先收集，不自动同时开工。

每轮输出最少只需三项：**本轮结论、依据/验证、下一问**。记录维护由AI协助，不要求用户额外做大量填表。

## 问题怎样相互连接

- 保留稳定编号，改标题、移动阶段不换ID。
- 拆分时保留父问题，为子问题分配新ID并互链；父项标“已拆分，尚未解决”，不能因为有了子项就算完成。
- 答案出现新问题时写“由哪个问题引出”，不把所有追问都当成解决前提。
- 重复问题合并时保留旧ID和去向；不删除提问轨迹。
- 新证据推翻结论时重新打开原问题，写原因与更新日期，不静默把原结论当成仍有效。
- 核心问题仍在阶段页；复杂到需单独文件时再拆出，通过链接保留入口。

例子（仅说明关系，不是新增已实施任务）：“曲线为什么卡顿？”可能拆为“数据到达多快”和“界面多久更新一次”；验证后又引出“暂停显示时是否继续记录”。保留这些因果关系比只存一篇最终答案更有用。

## 状态

待解决 → 推进中 → 待验证 → 已解决。按需要允许已拆分、合并、暂缓与重新打开，附具体原因。
“已有回答”与“本人能处理”分开：AI完成说明、代码生成或资料检索不自动关闭问题。本人验收没有发生就如实保留。

## 阶段怎样变化

第一至第七阶段是初始导航，28问是初始种子，不是固定试卷或必须全部做完的课表。实际需求、GitHub示例和实验结果可以补问题、调整顺序、合并或暂缓问题。
进入下一阶段只核对其必要前提，不要求清空上阶段全部疑问；当前仍只指定一个主问题。阶段范围改变时同步README、路线映射和CURRENT，保留修改原因。

## 需求与问题的区别

需求说明想达到什么、为什么；问题说明为了达到它还不知道什么。学习过程可以产生很多问题，只有经过取舍的问题进入当前任务。新发现不自动授权开发一个新系统，也不需要遇到一个问题就重做整个计划。

记录可使用[问题模板](QUESTION_TEMPLATE.md)。简单追问直接在阶段页或收件箱记三项即可，避免管理成本超过实际学习。
