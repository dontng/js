## 近期推进路线：从一次观察到最小上位机

整理日期：2026-11-02。以下是待验证的推进建议，关联P01-Q01、P01-Q02；不表示已完成实作，也不自动授权执行后续开发。七阶段仍作长期导航，本节只说明眼前怎样迈出第一步。

### 第一阶段终点

做出一个本人能解释、修改和验证的小工具，走通“连接设备 → 读取一个真实参数 → 显示并记录”。先验证读取链路，再按需要讨论发送控制指令、曲线与界面完善。Python作为暂定主语言，具体Qt绑定、绘图库和SDK接入方式由实际条件决定。

现在优先确定推进依据：这一步解决什么问题，靠什么证据验证，做到哪里可以进入下一步。不要求先学完Python和Qt，也不因出现一个新名词就扩成新的学习任务。

### 第一步：观察现有上位机的一项操作

选日常已经会做的只读操作，例如连接模组后查看实际转速。记录连接时选择的设备、通道和参数，操作顺序，以及连接前后的显示变化。未知项明确保留，不靠猜测补齐。

这里的“拆解”指黑盒观察：观察操作或条件与外部结果的关系，不能仅凭界面推断内部驱动调用、线程或报文解析方式。软件报告“连接成功”，也不一定证明模组已应答；需要日志、报文或资料进一步核实。

第一次只盯住一个参数，比较连接前、连接后，以及设备停止且允许断开时通过软件正常断开后的状态。关注是否有时间戳、接收计数或报文更新；数值不变不等于没有收到新数据。尤其要分清“测得零”“尚无数据”“旧数据”：界面无法区分时，也应如实记录为观察局限。

完成标准：能说清做了什么、显示了什么、有何证据，以及还缺哪条证据才能自己复现。观察结果用于推进P01-Q01，并明确P01-Q02需要核实的条件，不提前标记问题已解决。

### 第二步：确认数据怎样进入电脑

沿上述操作核实CAN适配器型号、厂商驱动与SDK、操作系统和架构、模组协议来源，以及是否有可运行的读取示例。界面观察负责提出问题，公开文档、厂商资料和实际实验负责验证机制；不能以猜测代替协议依据。

完成标准：选定一条有依据、可验证的只读接入路径。此时再筛选GitHub示例，判断哪些可以复用、哪些必须自己适配；不以star或fork数量作为进度。Windows库不默认可在Linux或WSL2使用。

### 第三步：做最小读取程序

先在终端中读取并记录一个参数，核对数值、单位和时间，验证正常关闭，以及断开或超时的处理。设备是主动上报还是需要查询，按真实协议确定，不预设所有读取都必须发送请求。

完成标准：本人能解释连接、收发、解析、记录和关闭的关键流程，并能据证据缩小一次异常的范围。无设备时可用自造数据验证解析与记录，但不能算作实机通信成功。

### 第四步：把已验证的读取能力放进Qt窗口

复用已跑通的读取功能，先显示数值、连接状态和数据有效性，再按需要加入记录操作和曲线。PyQtGraph在需要绘图时再引入；是否fork现成上位机，由具体缺口和可理解的代码规模决定。通信等待时界面仍应可操作，显示刷新不必与每条报文一一对应。

完成标准：窗口能够显示已验证的数据，区分当前有效值、无数据和旧数据；本人能独立修改一项行为，并验证结果。框架选择、美化与后续集成均按实际问题推进。
