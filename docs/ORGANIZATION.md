# 文件整理规则

## 先判断手里是什么

- 用户需求、功能想法、疑问与阶段问题：放 [requirements/](../requirements/README.md)，新问题先记收件箱；外部原资料不混在这里。
- 别人的手册、教程、官方仓库或招聘信息：放 resources/；不知道如何分类，先放 resources/inbox/。
- 自己消化后的解释、错误认识的纠正、排错方法：放 learning/。
- 为验证一件事而写的代码、步骤和结果：放 labs/，代码与记录同目录。
- 已经有持续用途、需要维护的程序：放 tools/。
- 计划、当前任务和系统条件：放 docs/。

无需同时抄写三遍。一份资料登记来源，一个实验引用它，实验得到的可复用结论再写成学习笔记。

## 命名

- 知识笔记按主题：learning/can/frames.md。主题目录有内容时再建，不预铺空目录。
- 实验按顺序和问题：labs/001-can-receive/；编号不表示已完成。
- 工具按职责：tools/can-monitor/、tools/ros2-bridge/；这些只是未来命名示例。
- 收件按日期和内容：resources/inbox/2026-11-02-can-box-manual.md。
- 一个实验中的截图等附件放该实验 assets/；资料附件放对应主题目录 assets/。能链接官方原文就不重复存副本。

## 一份资料的流转

1. 先记标题、来源链接或文件出处，以及“为什么收它”，可使用[资料模板](../templates/resource.md)。
2. 有空再判断：本轮要用、以后可能用、重复或无关。无关内容删除不等于学习损失。
3. 正式收录时，登记到[资料索引](../resources/SOURCES.md)，按需创建主题目录；从收件箱移走后修正链接。
4. 学习、实验引用来源编号，例如 R001。只有自己验证过的部分才写已验证。

## 实验和工具的区别

实验只回答一个问题；工具承担连续使用任务。实验首次跑通后仍保留原记录；确有维护需求再把通用实现整理到 tools/，文档互相链接。
不同工具初期可以独立运行；出现至少两处真实复用需求再抽公共代码，暂不建立庞大统一框架。
没有代码时不创建 src/、tests/、依赖文件和构建配置；开发开始后按实际语言及工具添加。

## 状态与维护

统一使用：待确认、待实验、已验证、暂缓。记录验证环境和日期；AI 草稿默认待验证。
每完成一轮更新 CURRENT，实验失败也记录证据；不要用提交次数或代码量代替掌握程度。
招聘样本至少记日期、地点、学历、薪资口径、编码职责与来源，不把外包当成必然放宽学历。

## 公开仓库材料

只提交可公开资料、自造数据及独立代码。厂商 SDK 优先记官方获取链接，不整包转存；未知授权的二进制和公司文件先不入库。
本地 .gitignore 不是保密保证，提交前仍检查内容，也不以改后缀绕过归档规则。
