# 名词

这里沉淀围绕软件、硬件和通信问题逐步形成的理解，名词链接帮助回查和串联。文档是理解过程留下的结果，不以词条数量、篇幅或链接数量衡量学习进展。

## 收录原则

> 容易得到也就容易失去，很难得到也就很难失去。

这句话提醒我们珍惜亲自追问、辨别和修正后得到的理解，不是要求故意把学习变难。AI迅速生成一篇完整的 Markdown，不等于这份知识已经成为自己的东西；方便查阅的解释也不能代替实际理解。

遇到不懂的名词，先保留问题，围绕真实疑问讨论；需要时结合公开例子、操作或代码尝试。等能够用自己的话解释关键关系，或据此判断下一步怎么做，再把值得回看的理解整理下来。不要求每个词都做实验，但不能只凭AI已经给出答案，就算完成学习。

记录应保留问题从哪里来、原先哪里不明白、怎样修正理解，以及当前能用它判断什么；这些内容按实际需要写，不设统一模板。还没弄清的地方明确留下疑问，不由AI补成看似完整的结论。面向公开项目时，只保留通用问题、公开依据和独立示例。

不因出现一个新名词就自动生成一篇文档，不为了点亮链接批量制造内容，也不强制一词一页。现有16篇解释只是初始参考，不代表已经经过本人消化；后续随讨论逐步修订，不急着全部扩写。

## 怎样使用与维护

使用普通 Markdown 相对链接，在 GitHub 中即可点击，无需 Obsidian 或插件。正文链接说明名词之间的关系，页尾“哪些名词与它有关”列出引用当前名词的页面，提供反向跳转。反向列表是写在文件里的内容，并非 GitHub 自动生成；以后改动关联时同步维护。

本目录内的所有 Markdown 链接都指向本目录的文件，不跨到其他笔记、需求或实验。参考来源用纯文本网址保留，供需要时复制查证，不做成文内跳转链接。其他目录保持原样，只从 docs 的学习页提供一个普通入口。

篇幅和拆分跟着实际问题走，不限定几句话，也不为了完整而扩写；只链接有解释关系的名词，不把所有词互相连满。增加名词时检查目标页存在，并更新被引用页面的反向列表。这里只放通用解释，不放个人资料、内部原件或实验记录。

具体设备是否支持某种接口或参数，仍需看对应型号的说明；通用名词解释不等于实机验证。

## 待解释

目前没有待解释名词。以后在本节用普通列表收词，例如“- 新名词”，暂不创建空页或空链接。经过讨论形成值得保留的解释后，再将相应入口补成链接，并核对正文和反向关联。链接点亮表示有解释可查，不表示本人已经掌握。

## 检查

脚本只检查文件和链接结构，不能判断理解是否形成、内容是否值得收录；检查通过不能作为批量生成文档的理由。

在项目根目录运行：

```bash
python docs/wiki/check/links.py
```

脚本只读取 wiki 顶层的名词页和本目录文件，不改写内容。它检查失效或越界链接、空壳解释页、目录是否漏收名词、正文引用有无反向链接，并提示已有解释但正文未链接的位置。脚本本身保存在 check 子目录，不算名词页。

名词标题即文件名，待解释名词只记在本页“待解释”列表，不另建数据库。新增解释后运行检查，由维护者核对并补链接；脚本不会猜测尚未收录的术语，也不会替代内容审核。漏链接按每页每词提示一次，同页已经链接过的词不重复提示，重叠名称优先匹配较长名称，标题、代码、已有链接和来源行不参与提示。只支持这里使用的普通行内 Markdown 链接，不作为通用 Markdown 解析器。
