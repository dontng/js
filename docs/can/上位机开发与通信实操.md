## 一、上位机与关节控制的本质关系

### 1. 通信管道 vs 业务语义
* **COM 口（串口）的定位**：电脑设备管理器中识别出的 COM 口，通常是 USB-to-CAN 盒（如周立功、创芯科技等）提供的虚拟通信管道。它只负责将上位机下发的二进制字节流通过差分电平（$CAN\_H$ / $CAN\_L$）打到总线上。
* **上位机的核心角色**：
  * **编码（Pack）**：将人类易读的高级物理量（如目标转速 $100\text{ rpm}$、目标角度 $90^\circ$、目标力矩 $2.5\text{ N}\cdot\text{m}$）转化为微控制器（MCU）能够识别的二进制/十六进制数据帧（Payload）。
  * **解码（Unpack）**：将关节模组回传的原始字节（温度、三相电流、绝对值编码器数值、故障码）换算为带量纲的物理变量并在 GUI 呈现。

### 2. 控制的本质：写寄存器与切换状态机
* 上位机**不是**在物理电路上直接调整电机的电压或电流。
* 模组内部集成有 FOC（磁场定向控制）驱动器、电机、编码器与减速器。上位机是通过报文向驱动器写入**控制模式（位置/速度/力矩模式）**与**目标设定值**。
* 驱动器内部的 MCU 负责以 $10\text{ kHz}\sim 20\text{ kHz}$ 的高频执行闭环 PID 运算，并向逆变桥输出 PWM 驱动电机。

## 二、敏捷认知路线：“四步穿透法”

拒绝一开始陷入庞大的 OSI 七层抽象模型。采用端到端反馈闭环，驱动系统认知的自然生长：

```
[步骤 1: 穿透弹] ──► 20行脚本硬编码发 Hex，关节动一下 (建立物理正反馈)
       │
[步骤 2: 参数化] ──► 提取变量函数 (输入角度/速度 ➔ 输出字节流)
       │
[步骤 3: 双向闭环] ──► 建立接收解包，抓取温度/电流/角度遥测数据
       │
[步骤 4: 保护与壳] ──► 引入急停、超时重置保护与 GUI 交互界面
```

1. **第一步（穿透弹）**：
   * 在 CANPro 等调试工具中抓取一条成功使能或正转的固定报文（如 `ID: 0x141`, `Data: 0xA2 0x00 ...`）。
   * 使用 Python 驱动硬件，不写任何类与架构，把这几位十六进制硬编码打出去，确认物理链路闭环。
2. **第二步（参数化）**：
   * 观察转速从 $100$ 变为 $200$ 时哪几个字节在变动。
   * 引入缩放因子（Factor/Offset）和结构体打包工具（如 Python `struct.pack`），实现人话向字节的转换。
3. **第三步（双向闭环）**：
   * 开启后台监听，解析模组上报的响应报文，建立对延时、丢包与遥测刷新的感性认知。
4. **第四步（保护与工程化）**：
   * 加入急停（E-Stop）机制与心跳超时断电联锁，增加多线程防止界面卡死。

## 三、报文抓包与协议类型识别法则

通过调试软件导出的列表文件（List / CSV / TXT），无需盲猜即可通过特征模式判断协议类型：

### 1. 通信方向判定
* **Tx（Transmit）**：上位机（电脑）主动下发至总线的报文。
* **Rx（Receive）**：外部设备（关节模组）回传至电脑的报文。

### 2. 国际标准 CANopen / CiA 402 指纹特征
若报文符合以下规律，判定模组运行标准 CANopen 协议：
* **ID 分布（预定义连接集）**：
  * 心跳报文：`0x700 + NodeID`（DLC=1，数据通常为 `0x05` 运行态或 `0x7F` 预操作态）。
  * SDO 请求/应答：上位机发 `0x600 + NodeID`，模组回复 `0x580 + NodeID`。
  * PDO 周期同步：分布在 `0x180+ID`、`0x280+ID`（TxPDO）及 `0x200+ID`、`0x300+ID`（RxPDO）。
* **SDO 首字节命令字（Data[0]）**：
  * `0x40`：读寄存器请求。
  * `0x23` / `0x2B` / `0x2F`：分别代表写 4 字节、2 字节、1 字节数据。
  * `0x60`：模组回复写入成功。
* **CiA 402 核心对象字典索引（Data[1]~Data[2]，小端序）**：
  * `40 60` ➔ 索引 `0x6040`（控制字 Controlword，用于使能/去使能）。
  * `41 60` ➔ 索引 `0x6041`（状态字 Statusword）。
  * `FF 60` ➔ 索引 `0x60FF`（目标速度 Target Velocity）。
  * `7A 60` ➔ 索引 `0x607A`（目标位置 Target Position）。

### 3. 私有自定义协议特征
* 报文 ID 固定（如 `0x140 + ID`），无 `0x600/0x700` 区间。
* 数据载荷首字节多为固定功能码（如 `0xA1` 读状态、`0xA2` 速度环、`0xA4` 位置环）。
* 字节末尾可能带有异或和（XOR）或固定 CRC8 校验。

## 四、Python 上位机核心架构与代码范式

### 1. 纯协议编解码器（Codec）
```python
import struct

class JointCodec:
    """协议编解码层：纯算法，与底层物理硬件收发解耦"""

    @staticmethod
    def pack_velocity_cmd(motor_id: int, target_rpm: float) -> tuple[int, bytes]:
        """打包速度控制帧（以典型私有协议为例：小端序，缩放因子 0.01）"""
        can_id = 0x140 + motor_id
        # 命令码 0xA2, 保留 3 字节, 目标速度转为 int32 (0.01 rpm/LSB)
        raw_speed = int(target_rpm / 0.01)
        payload = struct.pack("<B3xi", 0xA2, raw_speed)
        return can_id, payload

    @staticmethod
    def unpack_telemetry(payload: bytes) -> dict:
        """解包模组回传数据（假定 8 字节：温度、电流、转速、角度）"""
        if len(payload) < 8:
            return {}
        # 1字节温度(int8), 2字节电流(int16), 2字节转速(int16), 2字节编码器原始值(uint16)
        temp, current_raw, speed_raw, encoder_raw = struct.unpack("<bhhH", payload[:7])
        return {
            "temperature_c": temp,
            "current_a": current_raw * 0.01,
            "speed_rpm": speed_raw,
            "angle_deg": (encoder_raw / 65535.0) * 360.0
        }
```

### 2. 双线程 I/O 架构模型
上位机绝不能在 GUI 线程中直接死循环读写总线，应采用标准双线程解耦模型：

```
[GUI / 业务控制线程] 
      │ 下发目标 (thread-safe queue)
      ▼
┌──────────────────┐      CAN API       ┌──────────────┐
│  通信发送工作线程  ├───────────────────►│  USB-CAN 盒  │
└──────────────────┘                    └──────┬───────┘
                                               │
┌──────────────────┐      CAN API              │ 接收中断/轮询
│  通信接收工作线程  │◄────────────────────────┘
└────────┬─────────┘
         │ 解析为字典后回调通知
         ▼
[数据大盘 / 曲线绘制 / 状态监控]
```
