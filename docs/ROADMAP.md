## 目标与起点

起点：从 CAN 基础概念、参考程序与最小通信实验开始。
终点：独立完成设备通信、桌面工具和自动化测试，并由 ROS2 节点调用同一套设备接口，实现状态发布、查询和可反馈、可取消的模拟运动任务。
职业目标：机器人行业的软件测试开发、自动化工具和应用开发。当前关节模组是实践入口，不限制以后产品类型。

本文件是项目安排，所有阶段当前均未验收。完成代码不等于完成学习，必须通过独立修改、解释和复现验收。

## 第一条主线的参考成果

- Python 设备核心：连接、读取状态、控制请求、错误与时间信息。
- CAN/CAN FD 接入：调用已确认型号的厂商 SDK；不自行实现底层驱动。
- 模拟设备：不接实物也可演练成功、超时、故障、断开等场景。
- 桌面界面：连接状态、参数、反馈、曲线、日志。
- 自动化测试：复用设备核心，不依赖鼠标点击。
- ROS2 接口：复用设备核心，不重写设备协议。
- 示例、测试结果和故障记录：可重现、可解释。

先采用 Python；桌面阶段优先评估 PySide6，最终以设备 SDK 和运行环境验证结果为准。CANopen 或厂家私有协议按实际资料决定，不预设。ROS2 目前优先参照 Ubuntu 22.04 + Humble，在接入前根据目标 SDK、主机系统和依赖支持情况复核。

## 分阶段安排

各阶段工时为新增投入，包含理解、实现、实机验证及复盘，不是保证工期。

### 0：建立基线（6—10 小时）

取得并确认 CAN 盒型号、驱动与 SDK、操作系统、Python/库位数、模组协议、正常通信设置和可用设备时段。
从参考软件中选定一个只读功能，记录正常操作与结果。只在获准范围内阅读获准使用的参考代码；公开项目采用独立实现与可公开资料。
产物：环境清单、连接说明、一个功能的往返过程说明。
验收：说清按钮、程序、CAN 盒、驱动板的作用；确认后续开发条件及缺失项。

### 1：看见信息，补足编码基础（20—30 小时）

先运行厂商接收示例，显示时间、报文 ID、长度、帧类型及原始数据；设置与设备实际支持能力匹配。
用真实只读反馈学习变量、函数、循环、异常，以及十六进制、字节顺序、正负数、比例与单位。
产物：最小接收程序、收发记录、人工解析示例。
验收：独立解释一条反馈；更换一个已知样例后能自行修改解析，并能验证错误解析不会冒充正确数据。

### 2：独立读取与通信排障（30—40 小时）

实现打开、配置、发送、接收、关闭；从协议说明构造读取请求，匹配响应。
处理多个反馈、超时、错误返回、旧数据和设备断开。区分传输确认与设备业务完成。
产物：无需现有上位机即可读取的命令行工具；最小模拟设备。
验收：独立新增一个读取项；能基于证据区分未发出、无响应、解析错误和设备拒绝。
CAN/CAN FD 的帧格式、两阶段速率和 BRS 结合实际配置学习；设备不支持的模式只在模拟或合适测试设备上验证。

### 3：建立可复用设备接口（30—40 小时）

将硬件接入、协议解析、设备功能和模拟设备分开。上层只调用 connect/read_state 等清晰函数，不重复拼装字节。
形成统一状态：数值、单位、设备标识、时间、数据有效性和故障。对关键解析、超时及故障路径做有意义的自动检查。
运动控制仅在工作现场确认的限值、许可和停止流程下验证；软件停止不等于硬件急停。
产物：可被其他程序调用的 Python 设备模块及示例。
验收：更换模拟/真实设备入口，上层调用基本不变；新增参数无需修改所有界面或脚本。

### 4：桌面工具与自动化（45—60 小时）

界面实现连接、只读监控、日志、必要操作和后台收发，避免通信等待阻塞界面。
另写脚本复用设备接口：读取配置、执行步骤、等待反馈、判断结果、保存报告和异常上下文。
模拟无响应、数据过期、故障和中途断开，区分测试通过、产品失败和执行错误。
产物：可运行桌面工具、一项完整自动化测试、配置及报告示例。
验收：其他使用者可按说明使用；用户可独立修改一个测试步骤、复现一次问题并解释修复。
不先做多型号平台、账号系统、云端或复杂数据库。

### 5：跨环境与无设备运行（20—30 小时）

在 Linux/Ubuntu 中运行同一设备核心的模拟版及自动化测试；练习命令行、依赖安装、配置、日志和 Git。
验证真实 CAN 盒是否有 Linux 驱动/SDK。若无，先在 Linux 以模拟设备完成 ROS2 接入；必要时后续单独设计 Windows 通信代理，不能假设 DLL 可直接在 Linux 使用。
产物：另一环境的运行说明、模拟故障场景及结果。
验收：无特定实物设备时，仍可运行一轮测试并分析失败原因。

### 6：ROS2 接入与第一次集成测试（35—50 小时）

先用模拟设备编写 Python 节点，不直接控制实物。
- 话题持续发布设备状态与时间/有效性信息。
- 服务处理快速查询，如设备信息；长期运动不用阻塞式服务。
- 动作处理模拟运动，提供进度、完成结果和取消处理。
学习启动、参数、查看通信、记录回放，以及基本的时序与通信策略。
具备驱动条件后替换真实设备入口，核心协议解析不重写。真实取消与停止结果须由设备反馈确认。
产物：ROS2 软件包、启动配置、使用说明、一个成功和一个异常集成测试。
验收：通过 ROS2 调用 JS 设备核心；解释信息流；定位一次超时或取消失败；区分模拟经验与真实工作经验。

## 时间与推进方法

新增工时合计约 186—260 小时，另预留约 20% 处理设备、SDK、代码基础等不确定性：整体按约 220—310 小时规划。
每周 8—10 小时有效工作实践，约 6—9 个月；前三个阶段后根据实测速度重新估算。
以验收为准，不以代码生成量或日历时间为准；每 10 小时检查一次能否独立解释和修改。

每次参考学习围绕一个具体问题：先观察正常操作，再追代码和依据，独立实现最小修改，验证结果，留下简短经验记录。
AI 可协助解释、生成和审查，但用户必须亲自运行、修改及复现。每阶段至少一次不看现成答案的同类修改。

## 第一周工作

1. 确认 CAN 盒、SDK、系统与协议来源，列出缺失条件。
2. 选读取位置或设备信息作为唯一主线，追踪一次正常往返。
3. 跑通厂商接收示例；实物条件不足则先用明确标为模拟的数据练习。
4. 人工解释一条反馈，再将解释写进最小程序。
5. 保存一次可复现结果，用户口述过程并独立修改一处解析。
